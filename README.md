# Tranche

**The delivery plan where money is a dependency.**

Small studios plan the work in one tool and chase the money in another, so the plan keeps pretending the client has paid. In Tranche the money is part of the plan. Every phase of a client project ends in a PayPal payment gate, and the work after a gate stays locked until the client's money arrives. A Claude agent does the money work a careful studio manager would do. Plain code makes sure the agent can never pay anyone on its own.

- Live demo: https://tranche-kohl.vercel.app (access code `northwind-judge`)
- Video (under 3 minutes): _added before submission_
- Built for the PayPal AI Hackathon, November 2026. MIT licence.

## What happens in the demo

The demo project is a $12,000 brand site for a coffee company, run by a three-person studio. It has four payment gates: a $1,000 kickoff deposit and three milestone payments.

1. **Deposit hold.** The agent asks the client for the kickoff deposit as a PayPal hold. The client approves it on PayPal and the money is held, not taken. That is enough for work to start.
2. **Capture and invoice.** When the first phase is delivered, the agent captures the held deposit and raises the PayPal invoice for the next gate. The client pays it on PayPal's own invoice page.
3. **Late payment.** When an invoice goes past its due date, the agent sends one PayPal reminder. It then tells the plan the truth: the gated work moves to the date the money is now expected, and the Gantt shows every task that moved and by how many days.
4. **Crew pay.** When a phase is paid for, the crew who delivered it are owed their fees. The agent proposes one payout for exactly what is owed. A person reads it on a screen the model does not write to and approves it. Plain code checks it against the mandate that person signed, and only then does PayPal Payouts send the money.
5. **Safety test.** One tab plays a compromised agent. It forges payouts to a stranger, over the cap, before the client has paid, and without approval. It also plants a project note that tries to give the agent orders. Every forged payout is refused before any PayPal call, and the agent flags the note and ignores it.

## How PayPal is used

| Step | PayPal API | How it is called | Code |
|---|---|---|---|
| Kickoff deposit hold, then capture | Orders v2 (`intent: AUTHORIZE`) and Payments v2 (authorize, capture, void) | PayPal Server SDK for TypeScript (`@paypal/paypal-server-sdk`, generated by APIMatic) | `lib/paypal/orders.ts` |
| Milestone invoice: create and send | Invoicing v2 | PayPal Agent Toolkit (`create_invoice`, `send_invoice`) | `lib/paypal/toolkit.ts` |
| Reminder for a late invoice | Invoicing v2 | PayPal Agent Toolkit (`send_invoice_reminder`) | `lib/paypal/toolkit.ts` |
| The agent reads invoices itself | Invoicing v2 | PayPal Agent Toolkit tools handed straight to Claude (`list_invoices`, `get_invoice`) | `lib/agent.ts` |
| Check payments, record a payment made off PayPal | Invoicing v2 | REST | `lib/paypal/rest.ts` |
| Pay the crew | Payouts v1 | REST, one batch per approved proposal, with `PayPal-Request-Id` and a fixed `sender_batch_id` so a retry can never pay twice | `lib/paypal/rest.ts` |

Everything runs against the PayPal sandbox. Sandbox webhooks are unreliable, so Tranche checks PayPal at the start of every agent run and whenever someone presses "Check PayPal".

## How the AI is used

The agent is Claude (`claude-opus-5-5`, adaptive thinking, low effort by default) in a plain tool-use loop. The code is in `lib/agent.ts`, and its replies stream to the browser over server-sent events (`app/api/agent/route.ts`). Each run starts with the current project state and the operator's message. Its tools:

- `request_deposit_hold`, `capture_deposit`, `raise_invoice`, `check_payment`
- `send_payment_reminder`, `reschedule_after_late_payment`
- `propose_crew_payout`, which only proposes and never pays
- `flag_note`, for notes that try to give it orders
- `get_project_status`, plus the Agent Toolkit's `list_invoices` and `get_invoice`

A second use of Claude lives in the Books tab, where AG Studio's built-in agents run on `claude-sonnet-5-5` (see Sponsor tools).

The agent decides what needs doing on a given day. It answers questions without acting, raises each invoice once, and explains in a few plain sentences what it did and what the operator should do next. It has no tool that sends money.

## Why the agent cannot pay anyone

A payout goes out only when all eight checks in `lib/mandate.ts` pass. They are plain code with no model involved:

1. A mandate exists, and its signature is genuine.
2. The mandate has not expired.
3. Every payee is on the mandate's allow-list.
4. No single person is paid more than the per-payout cap.
5. The total paid out stays inside the mandate's budget.
6. The money has already been collected from the client.
7. The proposal has not been decided before.
8. A person approved this exact proposal. The approval is bound to a hash of the payee list and the amounts, so changing one name or one cent voids it.

Approved payouts are written to a hash-chained receipt log. Project notes reach the model wrapped as information, never as instructions, and the agent is told to flag any note that tries to give it orders.

## Sponsor tools

- **Bryntum Gantt** (`components/gantt/`). This is the plan board. Payment gates are milestones, and the work behind each gate depends on it, so a late payment visibly pushes the work after it. It also shows the critical path, the original plan as a baseline, and a "today" line that follows the demo clock. Editing a task in the Gantt saves it back to the plan. The trial bundle is loaded at runtime from `public/vendor/bryntum/`, which `scripts/copy-bryntum.mjs` copies from `node_modules`. It is not bundled, because bundling it ran the build out of memory.
- **AG Studio** (`components/books/`). This is the "Books" tab, an AG Studio workspace over the project ledger: receivables, crew pay, payouts, tasks, activity and the signed mandate. It has a custom Mandate widget, a theme that matches the app, KPIs, payment gates by status, crew pay and a receivables grid. Switch to "Ask and build" and AG Studio's own agents (lead, Page, Widget and Data) run on Claude through a small adapter, a swapped-in LLM harness (`components/books/claudeAdapter.ts`, server half in `app/api/ai/books/route.ts`, which keeps the key on the server). Ask a question and the agents read the data. Ask for a chart and they add it to the page and configure it. The datasets are read-only, so nothing in Books can move money.
- **APIMatic Context Plugin.** The PayPal Server SDK context plugin was installed into Claude Code (log in `docs/apimatic/install.log`). Its `typescript-getting-started` and `typescript-error-handling` skills shaped `lib/paypal/orders.ts`: one shared `Client` with client-credentials auth for the sandbox environment, `OrdersController` and `PaymentsController` for the hold flow, and `ApiError` mapped to plain sentences with PayPal's issue code kept.

## Try it

- **Live demo:** https://tranche-kohl.vercel.app
- **Access code:** `northwind-judge`. Type it into the Agent panel on the right and press Save. The code only keeps bots from spending the demo's PayPal sandbox and Claude calls.
- **Pay as the client.** When a gate asks for the client's money, open the PayPal link on its card and log in with the PayPal sandbox client account. The app shows that test login under the payment gates. It is a sandbox account and holds play money only. If you would rather not log in, the gate card's "Record payment" button marks the PayPal invoice as paid for you.
- **A quick path through it.** Press "Run today's check" and approve the deposit hold on PayPal. Then press "+3 days" a few times and run the check again after each one. Pay the invoices it raises, and approve the crew payout on the Money out tab. Let one invoice go late to watch the plan move. Then try the Safety test tab.
- Each visitor gets their own project, stored in their own browser. "New demo" starts again from day 1.

## How it is built

- Next.js 16 (App Router, route handlers), React 19, Tailwind 4, TypeScript.
- No database. The browser keeps the whole project as a workspace signed with HMAC (`lib/sign.ts`). Every API call sends it, the server checks the signature, applies the action, and signs the next version. The client cannot change its own numbers. It could replay an older signed copy, which is acceptable for a demo but not for production.
- Demo clock. "+1 day" and "+3 days" move the project's own date so a month of work fits in a three-minute video. PayPal stamps its records with real dates, so a PayPal invoice shows today's date while Tranche shows the demo date.
- The optional `TRANCHE_ACCESS_CODE` puts the agent and every PayPal write behind a code. The agent and every route that changes something are rate-limited.

### Run it locally

You need Node 20 or newer, a PayPal sandbox REST app, five sandbox test accounts (one business, one client and three crew) and a Claude API key.

```bash
npm install
cp .env.example .env   # then fill it in
npm run dev            # http://localhost:3000
```

`npm run dev` and `npm run build` first copy the Bryntum Gantt trial bundle into `public/vendor/`. That folder is not committed.

## Limits, honestly

- Sandbox only. Payouts come out of the sandbox business account's balance. Each full demo run pays the crew $6,700 of play money.
- The workspace lives in your browser. Clearing site data starts a new demo.
- Bryntum Gantt and AG Studio run on trial licences, so you will see their trial notices. They are not covered by this repository's MIT licence.
